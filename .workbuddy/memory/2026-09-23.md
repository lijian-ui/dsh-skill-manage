## 调研：官方桌面版 vs Web 版插件集成差异（已订正）
- 目的：用户听说 web/桌面插件不通用，让我核对源码。
- **重大订正（用户指出 `dsh plugin --profile web add` 也走 pnpm，质问与桌面何异）**：
  - 我去读了 `apps/cli/src/args.ts`（`plugin` 子命令=把参数转发给 profile 目录的 pnpm）、`apps/cli/src/plugin.ts`（`reconcilePlugins` 按是否已装且声明 `dsh.bundle` 自动维护 `dsh.profile.bundles`）、`packages/boot/app-boot/src/profile.ts`（profile 模板：web=`['dsh-base','dsh-web-app']`）。
  - **结论：web 与桌面没有两套插件格式，装载机制是同一个**——都是「pnpm 安装带 `dsh.bundle` 的 npm 包 → 自动并入 `dsh.profile.bundles` → 启动时 composeEntries 拼装 `dsh.bundle.patch`」。
  - 唯一差别：① 谁来按安装键——CLI（`dsh plugin --profile <X>`，X∈web/tui/headless/自定义）vs Electron 应用（桌面 profile，CLI 显式 `rejectElectronProfile` 拒绝碰 `desktop`）；② 第三方差别只是"第一方内建 bundle 走构建时，第三方插件两端都走运行时安装"。
  - "不通用"真实来源只有三种：版本割裂（`schema` vs `create`）、作者用 `dsh.client.platform` 主动限定、依赖某端独有 bundle。桌面/web profile 基础 bundle 都是 `['dsh-base','dsh-web-app']`，客户端运行时同套。
  - **我上一条「Web=构建时打包、桌面=运行时安装」说法是错的**，已在手册第 10 节彻底改写订正。
- 参考插件现状：已自带 `dsh.bundle.patch` + `dsh.client.*` + 自插入 patch + `create` 契约 → 跨平台（web + 官方桌面）直接用，无需为某端重写。

- `disable-model-invocation` / `user-invocable` 是技能 frontmatter 里的两个可见性开关字段，**不是管理工具**。

## 最终根因：客户端调了不存在的 `sessions.currentProvideInfo`（2026-09-23）
- 用户装 0.2.3 后回报：面板仍显示「暂时无法读取技能。Cannot read properties of undefined (reading 'getSnapshot')」，并附上 host 日志——**日志显示 host 侧全通**：`[boot] host module imported` → `[apply] host apply running`（typert/settings/skills/sessions/agents/tools 全 true）→ `[register] typert manifest registered {"methods":[...6个]}` → `[tools] skill_manage tool registered`。
- **结论：0.2.3 的 inject 收窄修复是成功的**（host 半边已正常启动、manifest 已注册），报错发生在**客户端半边**——这正是日志分析法起效的证明。
- **真正根因（`src/client/index.ts:146` 原代码）**：
  `(ctx as SessionsCtx).get('sessions').currentProvideInfo.getSnapshot().sessionId`
  —— 官方 client `sessions` 服务（`ISessions`，来自 `@deepseek-ai/dsh-api-session-controller/client`）**根本没有 `currentProvideInfo` 属性**。该属性是当初凭空写错的，运行时为 `undefined` → `.getSnapshot()` 抛 `TypeError`。而 `currentSessionId()` 在 `listSkills: () => callRemote('list', currentSessionId())` 的实参位置同步求值，异常直接让 promise reject → UI 报错。
- **正确 API（对照官方源码核实）**：
  - `packages/api/session-controller/src/client/contract/sessions.ts:23` → `readonly list: ObservableSnapshot<SessionListState>`
  - `packages/api/session-controller/src/client/sessions/service.ts:69` → `interface SessionListState { ids; byId; current: SessionId | undefined; phase; ... }`
  - 官方同款读法：`ui-session/src/client/index.ts:355` `this.sessions.list.getSnapshot().current`；`ui-skill/src/client/index.ts:180` `sessions.list.getSnapshot().byId[sessionId]?.cwd`
  - 即正确写法 = `ctx.get('sessions').list.getSnapshot().current`
- **官方"标准属性"正解（更规范的做法，本次未采用但已记录）**：`settings.section` 是 `scope:'root'` 槽位，其组件会自动收到 `GlobalStandardProps`，其中 `useSessions`（定义于 `ui-session/src/client/index.ts:104-110` 的 `declare module`）是选择器 hook：`props.useSessions(s => s)` → `{ current, byId, phase }`。官方 `ui-settings-unarchive-sessions/src/client/ArchivedSessionsSection.tsx:58-59` 即这么取。session 域槽位另有 `sessionId`/`useSession`/`useProjection`（`SessionStandardProps`）。
- **修复内容（0.2.3 → 0.2.4）**：
  - `SessionsCtx` 类型改为 `{ get(key): { list?: { getSnapshot(): { current?: string } } } | undefined }`。
  - `currentSessionId()` 重写为 try-catch + 全链可选链，失败返回 `undefined`（视为"无当前会话"，host 侧回退全局层），绝不阻断列表。
  - 顺手清掉 UI 里误导性提示 `noSession`（"打开一个会话后即可查看该会话的技能。"）——设置面板本就该显示全局技能；同时移除组件 props/destructure 里的 `currentSessionId` 入参与 i18n 的 `noSession` 键（孤儿键一并清理）。
- 构建产物核对：`lib/client.js:909` `return ctx.get("sessions")?.list?.getSnapshot()?.current;`，`currentProvideInfo` 已彻底消失。
- 发布 **0.2.4** 成功（`+ @lijian-ui/dsh-skill-manage@0.2.4`；约 90s 后 `npm view` 确认 version/tarball 可查）。
- **教训（重要）**：日志里的 host/client 分界是定位跨半边问题的关键——host 日志全绿就应当立即转向客户端排查，不要继续在 host 侧猜。此前两轮（0.2.2 猜 registry 崩、0.2.3 猜 inject 挂起）都在 host 侧浪费时间；0.2.3 的 inject 修复恰好也是真问题（只是不是当时报错的那个），两者叠加才把 0.2.3 的报错**换成**了客户端的这个错，从而暴露出来。

## 收尾：`cannot get property "skills" without inject`（0.2.4 → 0.2.5，2026-09-23）
- 用户装 0.2.4 后回报：面板错误变为 **`skillManage.list failed: gateway/internal: cannot get property "skills" without inject`**（host 日志依旧全绿）。这是个**进步信号**——0.2.4 修好了客户端会话读取，RPC 终于打到 host，暴露出 host 侧下一个真实缺陷。
- **根因（cordis inject 守卫）**：cordis 把服务声明为 `ctx` 上的 getter，**只有列在 `inject` 里的服务才允许 `ctx.skills` 这种直连属性访问**。0.2.3 我们把 `skills`/`agents`/`sessions`/`tools` 从 inject 摘掉（为修硬依赖挂起），但代码里仍有 3 处直连属性访问 → getter 主动抛错。
  - `remote.ts` 原 239 行 `(this.ctx as Context & { agents: ... }).agents.get(sessionId)` —— **在 try/catch 外面？不，在 try 内但 249 行在外面**；实际抛错点是 249。
  - 原 249 行 `return (this.ctx as Context & { skills?: Registry }).skills` —— **在 try/catch 之外**，`registryFor` 被 `viewFor` 调用 → `list` 直接抛 → 报错。
  - 原 407 行 `(this.ctx as Context & { sessions: ... }).sessions.list()` —— 在 try 内但同样是直连守卫。
- **修复（3 处，`src/remote.ts`）**：
  - `registryFor`：`agents` → `ctx.get('agents')` + 可选链；`skills` → `ctx.get('skills') as Registry | undefined`。
  - `workspaces`：`sessions` → `ctx.get('sessions')` + `typeof sessions?.list === 'function'` 守卫。
  - 已 grep 全仓 `this.ctx.`/`(ctx as Context & {...}).<svc>` 确认无遗漏；`sessionFor`（256 行）此前已是 `ctx.get` 写法。

- 构建产物核对：`lib/index.js:1350/1356/1362/1520` 均为 `this.ctx.get("agents"/"skills"/"sessions")`，直连属性归零。
- 发布 **0.2.5** 成功，`npm view` 确认 version/tarball 可查。
- **本轮教训（已写入 MEMORY.md）**：`inject` 与 `ctx.<svc>` 是配套的——**摘 inject 必须同步把全仓 `ctx.svc` 改成 `ctx.get('svc')`**，否则 getter 主动抛 `cannot get property "X" without inject`。注意这不是"服务不存在"（`ctx.get` 能拿到），而是"没声明就不给点属性"。
